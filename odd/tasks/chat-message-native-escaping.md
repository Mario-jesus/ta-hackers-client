## Objective and authorization

The official 1.229 chat builder pre-escapes the chat message with .NET `Uri.EscapeDataString` before the URI is canonicalized and checksummed. This client instead form-encodes the whole query and then globally unescapes colons. The divergence this created was byte-level in the signed wire URI only: for messages containing colons the signed URI emitted raw `:` where native emits `%3A`, and `*` stayed raw where native emits `%2A`; both encodings decode back to identical message text, so no decoded message text was corrupted. The bounded authorized fix makes the chat message field use a native-equivalent RFC 3986 data escape while every other chat field and all non-chat requests keep their existing safe behavior. This aligns the outgoing URI with the observed native flow, but does not prove or claim a server-side root cause for the user's send 500.

Authorization: the user explicitly approved local fix plus regressions and exactly ONE original-message live test in the approved chat room with the approved `configs/apple.conf` configuration. The parent session owns that live test; this worker performs offline work only — no game, backend, network, config or credential access. The live result will be recorded by the parent.

Round-2 controlled backend evidence localized one server constraint: percent-escaped bangs (`%21`) inside the message field were rejected with an empty 5-class send response, while the identical decoded text with a literal bang in the signed wire bytes published. The client therefore applies an explicit backend-compatible normalization of only that final wire byte shape, preserving the RFC 3986 escape stage and every other escaped shape. This is cause evidence for percent-bang sends, not the ultimate 500 root.

Round-3 controlled backend evidence extended the same constraint to asterisks: the production percent-asterisk wire for `A*B` (`A%2AB`) was rejected (500, empty, 0 bytes, no fresh own exact echo), while the same message with only `%2A` exposed as a literal `*` and the unmodified hash formula published (200, 75 bytes, fresh own exact echo in the send response; follow-up read normal after the cursor; exactly two sends and ten RPCs, no retries). The user explicitly approved applying the asterisk normalization plus ONE complete original room 69 live validation; that validation is granted, pending, and parent-owned.

Round-4 final validation: the user-granted complete original room 69 send executed exactly once through real, unmodified production source (canonical path unpatched, no monkeypatch), parent-owned and independently verified — auth/profile/display/send/display all HTTP 200, send 212 bytes with a structured echo of the own account id and exact text inside the send response, post-send display 200 with 0 new records after the advanced cursor, CLI exit 0 and `publication_confirmed` true; the echoed datetime is recorded only as a privacy-bounded string length (23 characters).
